**Цель:** дообучить `intfloat/multilingual-e5-small` на русскоязычных парах вопрос–контекст из SberQuAD и сравнить качество точного поиска до и после обучения.

# Часть I. Теория

## 1. Что решает модель

На вход поступает вопрос:

```text
Какое содержание селена в морской воде?
```

В корпусе есть сотни документов. Необходимо поставить выше документы, в которых содержится ответ, и ниже нерелевантные тексты.

Модель не извлекает короткий ответ и не генерирует его. Она решает задачу первого этапа QA-системы — **retrieval**, то есть поиск подходящего контекста. Найденный текст затем можно передать extractive QA-модели или LLM.

```text
Вопрос -> поисковая модель -> релевантные документы -> QA-модель/LLM -> ответ
```

## 2. Почему поиск называется семантическим

Обычный лексический поиск опирается на совпадения слов. Это полезно, но формулировки вопроса и документа могут различаться:

```text
Вопрос:   Кто создал язык Python?
Документ: Автором языка является Гвидо ван Россум.
```

Слова `создал` и `автор` различны, хотя смысл связан. Семантическая модель пытается разместить тексты с близким смыслом рядом в векторном пространстве.

## 3. Эмбеддинг текста

Эмбеддинг — массив чисел фиксированной длины:

```text
"Какое содержание селена в морской воде?"
                 ↓ encoder
[0.013, -0.082, 0.041, ..., 0.027]
```

У `multilingual-e5-small` один текст представляется вектором размерности 384. Координаты не имеют простых названий вроде «химия» или «география». Их смысл распределён и формируется обучением.

Хорошая embedding-модель должна давать:

- близкие направления векторов для вопроса и релевантного документа;
- менее близкие направления для вопроса и нерелевантного документа.

## 4. Как Transformer превращает текст в один вектор

### Токенизация

Текст разбивается на токены и заменяется их числовыми идентификаторами. Transformer возвращает контекстный вектор для каждого токена.

```text
текст -> токены -> Transformer -> [h1, h2, ..., hL]
```

Но для поиска нужен один вектор на весь текст. Поэтому используется pooling.

### Mean pooling

E5 использует усреднение токенных векторов с учётом attention mask:

```text
z = sum(mask_i * h_i) / sum(mask_i)
```

Padding-токены нужны, чтобы выровнять длины примеров в batch, но их нельзя включать в среднее. Именно поэтому используется маска.

### L2-нормализация

После pooling вектор делится на свою длину:

```text
z_normalized = z / ||z||₂
```

Длина результата становится равной единице. Тогда скалярное произведение двух векторов совпадает с cosine similarity.

## 5. Bi-encoder

Bi-encoder независимо кодирует вопрос и документ:

```text
q -> Encoder -> z_q
d -> Encoder -> z_d

score(q, d) = cosine(z_q, z_d)
```

В E5 фактически используется один encoder с общими весами, но входам задаются разные префиксы.

Главное преимущество: эмбеддинги документов можно вычислить заранее. При новом запросе вычисляется только один query-вектор, после чего выполняется быстрый поиск ближайших document-векторов.

Это отличается от cross-encoder, который объединяет вопрос и документ и запускает Transformer для каждой пары. Cross-encoder обычно точнее понимает взаимодействия слов, но слишком дорог для первичного поиска по большому корпусу.

## 6. Cosine similarity

Косинусное сходство измеряет угол между векторами:

```text
cos(q, d) = (q · d) / (||q||₂ ||d||₂)
```

После L2-нормализации знаменатель равен единице:

```text
cos(q, d) = q · d
```

Важно не абсолютное значение cosine, а порядок документов. Даже если все scores лежат между 0.6 и 0.9, модель полезна, когда релевантные документы систематически получают больший score.

## 7. Префиксы E5

Для асимметричного поиска E5 обучалась с префиксами:

```text
query: Какое содержание селена в морской воде?
passage: Концентрация селена в морской воде ...
```

Префикс сообщает модели роль текста. Вопрос обычно короткий и выражает информационную потребность, а passage длиннее и содержит сведения. Без префиксов качество E5 снижается.

## 8. Contrastive learning

Модели показывается правильная пара `(q, d⁺)`. Нужно увеличить similarity этой пары и уменьшить similarity вопроса с негативными документами `d⁻`.

Для вопроса `q_i` probability правильного документа в batch можно представить как:

```text
P(d_i | q_i) = exp(sim(q_i, d_i) / τ)
               --------------------------------
               sum_j exp(sim(q_i, d_j) / τ)
```

Loss — отрицательный логарифм этой вероятности:

```text
L_i = -log P(d_i | q_i)
```

Такой подход называют InfoNCE или Multiple Negatives Ranking Loss.

## 9. In-batch negatives

В batch из 16 правильных пар для каждого вопроса есть:

- один позитив — документ из той же строки;
- 15 негативов — позитивные документы других вопросов.

```text
q1 -> d1  positive; d2...d16 negatives
q2 -> d2  positive; d1,d3...d16 negatives
...
```

Это выгодно: не нужно отдельно хранить большое число негативов, а один batch даёт `16 × 15 = 240` сравнений с негативами.

Использован `NO_DUPLICATES` batch sampler. Он не допускает одинаковые тексты внутри batch, уменьшая риск считать один и тот же правильный контекст негативом.

## 10. Temperature

Temperature `τ` управляет резкостью softmax. В работе `τ = 0.01`, то есть scale loss равен `1 / τ = 100`.

Малая temperature сильнее подчёркивает небольшие различия cosine scores. Модель получает большой штраф, если негативный документ приблизился к позитивному. Слишком малая temperature может сделать обучение нестабильным, поэтому это полноценный гиперпараметр.

## 11. Почему старые отрицательные пары не передаются в loss напрямую

Выданные `trainval.pkl` и `test.pkl` содержат положительные и случайные отрицательные пары. Старый ноутбук обучался через `CosineSimilarityLoss` с метками 1 и 0.

В современной реализации для обучения взяты положительные пары, а негативы создаются внутри batch. Для retrieval это лучше соответствует реальной задаче: модель учится не просто назначать паре условный score 0 или 1, а выбирать правильный документ среди конкурентов.

Отрицательные test-пары сохранены для отдельной диагностики ROC-AUC, Spearman и cosine-margin.

## 12. Метрики поиска

### Accuracy@1

Доля вопросов, для которых релевантный документ стоит на первом месте.

### Recall@5

Доля вопросов, для которых правильный документ находится среди первых пяти:

```text
Recall@5 = найденные в top-5 / все вопросы
```

### MRR@10

Mean Reciprocal Rank учитывает позицию первого правильного результата:

```text
rank 1 -> 1.0
rank 2 -> 0.5
rank 5 -> 0.2
ниже 10 -> 0
```

Значения усредняются по вопросам. MRR особенно чувствителен к первым позициям.

### MAP@10

Mean Average Precision учитывает позиции всех релевантных документов. В нашем протоколе у каждого вопроса один релевантный документ, поэтому AP@10 совпадает с reciprocal rank, а MAP@10 — с MRR@10.

### nDCG@10

Normalized Discounted Cumulative Gain даёт больший вклад релевантным документам на верхних позициях и логарифмически уменьшает вклад с ростом rank:

```text
gain(rank) = 1 / log₂(rank + 1)
```

При одном бинарном релевантном документе nDCG@10 равно среднему discounted gain его позиции.

## 13. Pairwise-метрики

Дополнительно на 1000 позитивных и 1000 негативных test-парах рассчитаны:

- ROC-AUC — вероятность, что случайный позитив получит больший score, чем случайный негатив;
- Spearman — монотонная связь labels и similarity;
- средний positive cosine;
- средний negative cosine;
- cosine-margin — разность средних positive и negative scores.

Cosine-margin важнее абсолютных средних значений. После fine-tuning оба средних cosine уменьшились, но negative cosine уменьшился намного сильнее, поэтому классы разделились лучше.

## 17. Результаты retrieval

| Метрика | Baseline | Fine-tuned | Δ |
|---|---:|---:|---:|
| Accuracy@1 | 0.908389 | **0.923841** | +0.015452 |
| Recall@5 | 0.971302 | **0.980132** | +0.008830 |
| Recall@10 | 0.977925 | **0.990066** | +0.012141 |
| MRR@10 | 0.935134 | **0.948844** | +0.013710 |
| MAP@10 | 0.935134 | **0.948844** | +0.013710 |
| nDCG@10 | 0.945749 | **0.959014** | +0.013265 |

nDCG@10 вырос на `0.013265`, то есть приблизительно на **1.33 процентного пункта**. Это превышает ориентир +1 п.п. из углублённого варианта лекции.

Из 906 вопросов после обучения:

- 837 имеют правильный документ на первом месте вместо примерно 823 до обучения;
- 888 имеют правильный документ в top-5 вместо примерно 880;
- 897 имеют правильный документ в top-10 вместо примерно 886.

## 18. Pairwise-результаты

| Метрика | Baseline | Fine-tuned | Δ |
|---|---:|---:|---:|
| ROC-AUC | 0.998739 | 0.998798 | +0.000059 |
| Spearman | 0.863841 | 0.863944 | +0.000103 |

| Negative cosine mean | 0.734917 | 0.309927 | -0.424990 |

Снижение positive cosine само по себе не является ухудшением. После contrastive fine-tuning отрицательные пары отодвинулись гораздо сильнее. Margin увеличился примерно в 2.5 раза, а ranking-метрики выросли.

Это хороший пример того, почему нельзя задавать универсальный порог вроде `cosine > 0.8`. После обучения шкала scores может измениться, тогда как относительный порядок становится лучше.

## 19. Примеры изменения выдачи

### Крупное улучшение

```text
Вопрос: Чем соединены деки друг с другом?
Baseline rank: ниже 10
Fine-tuned rank: 1
```

До обучения top-1 был текст об анатомии приматов. После обучения первым стал контекст о корпусе скрипки, где прямо сказано, что деки соединены обечайками.

```text
Вопрос: Что позволяют предположить косвенные результаты?
Baseline rank: ниже 10
Fine-tuned rank: 1
```

После обучения найден контекст о водороде у поверхности Титана, содержащий точную формулировку вопроса.

### Локальное ухудшение

```text
Вопрос: Что предшествует постройке железной дороги?
Baseline rank: 1
Fine-tuned rank: 3
```

Модель стала сильнее связывать вопрос с другими текстами о строительстве железных дорог и опустила точный контекст ниже.

```text
Вопрос: Кто победил Нагайну?
Baseline rank: 8
Fine-tuned rank: ниже 10
```

Вопрос сформулирован неточно: в контексте Невилл не «победил», а убил Нагайну. Fine-tuning не исправляет все неоднозначные формулировки и может ухудшить отдельные случаи.

Полные выбранные примеры улучшений и ухудшений сохранены в `ranking_changes.csv`.

## 20. Анализ

Исходная E5 уже показала высокое качество, поскольку предобучена специально для многоязычного retrieval. Поэтому значительный рост сложнее получить, чем при старте с обычного языкового encoder.

Тем не менее, SberQuAD fine-tuning улучшил все основные ranking-метрики. Наиболее важные эффекты:

1. Правильный документ чаще поднимается на первое место.
2. Число пропусков за пределами top-10 снизилось почти вдвое: примерно с 20 до 9.
3. nDCG@10 вырос на 1.33 п.п.
4. Cosine-margin вырос на 0.20.

Ограничения эксперимента:

- использована только часть положительных train-пар;
- случайные и hard negatives не сравнивались отдельными экспериментами;
- у каждого тестового вопроса задан один релевантный документ;
- корпус содержит 906 документов, а промышленный поиск может работать с миллионами;
- для длинных контекстов используется усечение до 256 токенов.

В лабораторной работе построен полный pipeline семантического поиска: подготовка пар, кодирование E5, contrastive fine-tuning, точный поиск по корпусу и оценка ranking-метриками.

Код исходного ноутбука актуализирован под современный Sentence Transformers. Обязательная модель `multilingual-e5-small` дообучена на SberQuAD.
